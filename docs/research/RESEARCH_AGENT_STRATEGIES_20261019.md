## 对 InfoExplorer 的调整建议（尚未实现）

目标流程：明确研究范围 → 子问题/检索计划 → 搜索与读取 → 证据整理 → 判断缺口 → 继续或结束 → 生成报告 → 引用检查。

1. 规划必须说明子问题、时效/范围需求和所需证据类型，而不仅是生成同义关键词。只有缺少信息会显著改变搜索方向时才澄清，不强制每次提问。
2. 规划、覆盖判断和报告是职责，不必部署三个独立 Agent。首版用同一模型分阶段调用，程序控制状态转换；后续按需要演进为模型选择动作的有界循环。
3. 模型提出结构化动作及面向用户的简短理由，程序验证动作、预算和允许的工具。只允许检索、读取受控来源和结束；不授予终端、文件或数据库操作。网页仍作为不可信数据。
4. 对子问题记录已有证据、缺口、矛盾与来源时间。覆盖结论属于模型判断，不能当作已证实的事实。出现冲突优先追溯第一手资料，不按来源数量投票。
5. 首版“最多一轮补搜”仅是安全预算上限，不是无条件补搜或固定研究规则。资料够用可提前结束；无新信息、重复查询、预算耗尽或来源不可访问时停止，明确遗留问题。预算应版本化保存，调整需同步双端契约。
6. 引用分两层：程序验证引用存在、定位与 hash；进一步判断被引用段落是否支持结论。模型复核仍可能出错，不能声称自动证明事实。保留事实、推断与未知的区别。
7. 后续增加阶段事件、耗时/调用量、停止原因和检查点。当前失败后重试是新运行，不是真正断点续跑；恢复不能盲目重放有成本的外部调用。Java 管生命周期/持久化，Python 管研究执行，React 展示用户可读进度而非模型私有推理。
8. 多 Agent 留作可选扩展，适合确有独立研究维度的宽泛问题；先解决任务边界、全局预算、重复来源和结果合并。先做工具并发不等于已经实现多 Agent。

现有 SearXNG、受限下载、Trafilatura、稳定证据身份、按运行保存结果都继续复用。大公司拥有的搜索索引、训练模型和基础设施不能由这些组件等价替代；借鉴的是编排与工程方法，不承诺相同研究质量，也不要求购买其研究 API。

## 实施顺序建议

先补研究计划/动作/结束原因的契约与状态设计，再接模型规划、缺口判断和报告；随后增加阶段事件和检查点，最后按实际需求加入并行子任务。当前 v2 严格限定 direct/web-extract/modelCalls=0，不能直接把模型结果塞入旧契约，需显式演进并保持旧任务可读。

保留必要的契约、安全、失败恢复和真实链路验证。遵守用户此前“不建立问题集做新旧结果对比”的要求，本轮不创建评测集，也不宣称已经证明质量提升。
