## 下一批工作的依赖顺序

1. W1 已完成离线验证，维持与现有运行路由隔离；补充网络下载器时继续验证边界。
2. W2 环境准备与 W3 代码设计可独立推进。需要系统安装/重启时记录阻碍，继续 W3/W4 等不依赖环境的部分。
3. W4/W5 契约一起确认，避免 Python 单边输出 Java 不认识的字段；Java 编译前按约定停止用户运行实例。MySQL 迁移先临时库、再备份日常库。
4. W6 接真实存在的 API；在此之前只做明确标记的设计原型，不给现有页面添加无效功能入口。
5. W7 验证一次完整链路后进入 T1/T2，T3 最后启用。R1 与 W5 一起处理，不能把可靠性问题带入调度。

## 每批交付必须记录

- 目标、实际改动文件、兼容性和启用方式。
- 通过/失败/跳过/未运行的检查，以及是否联网、使用哪个数据库、是否调用模型。
- 环境阻碍、未解决问题；不把本机命令未找到推断为用户一定没安装过。
- 运行服务是否重启、日常数据库是否改变、是否需要用户输入凭据。
- 下一批可以自主执行的工作与确实需要人工操作的工作。

## 可以持续执行的边界

已有授权下，普通实现选择、代码修改、离线测试、修复和文档更新连续执行，不每一步索要“继续”。遇到必须输入凭据、系统组件安装交互、用户服务停止或日常库升级时，把需要人工的部分隔离，其余工作继续。任何 Git 初始化、提交、上传和新付费支出不包含在默认授权中。
